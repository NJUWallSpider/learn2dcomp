### 关键发现

- **0/8 干净求解** — 没有一个实例能在不使用人工变量的情况下求解
- **5/8 DW 失败** (artificial vars 2-9 个): 列生成无法覆盖所有 task 的整数解
- **3/8 TIME_LIMIT**: 120s 内 MIP 无法收敛

### 污染消除验证

旧 Oracle obj 模式: `Gurobi_obj + N × 1e8`（N = 人工变量数）
新 Oracle obj 模式: `Gurobi_obj + N × 1e5`（N 相同，仅惩罚系数从 1e8 变为 1e5）

例如 a15_t84_typeC_33:
- 旧: 6,564 + 9 × 100,000,000 = 900,005,964 ≈ 900,005,971 ✓
- 新: 6,564 + 9 × 100,000 = 905,964 ≈ 905,971 ✓

**模式完全吻合**，证明修复精准命中根因。

## 结论

1. **修复成功**: 1e8 污染已消除，人工变量使用被正确检测和报告
2. **Type C 大实例是 DW 方法的固有限制**: 不是代码 bug。knapsack pricing 子问题在 10s 限制内无法生成足够的列来支持整数可行解
3. **T-007 的 "19.36% gap" 现在可以正确解读**: 干净实例中位 gap 0.18%，8 个 Type C 是合法 DW 失败

## 经验教训

- **看到大数字不要急着修代码**: 1e8 污染是症状，根因是 DW 列生成在大实例上失败。修复后症状消失，但底层问题（列不足）仍在
- **污染消除 ≠ 问题解决**: 去除 1e8 后 obj 从 9e8 降到 9e5，但仍然远高于 Gurobi optimal（6,564）。DW 仍然失败，只是现在诚实报告了
- **Type C 实例特性**: 15-16 agents × 63-89 tasks，knapsack 子问题搜索空间大，10s pricing 限制可能不足以探索足够多的列
